Prérequis à débloquer

Sans ça, aucun produit ne pourra passer en vente. À vérifier en premier.

  • Accord Paid Apps signé et actif
    App Store Connect → Business → Agreements. Coordonnées bancaires + fiscalité renseignées. Tant que c'est « Pending », les produits restent bloqués.
  • Bundle ID com.trainwise.appli confirmé
    C'est l'identifiant que RevenueCat devra pointer. Il doit correspondre exactement à celui de l'app.
🚧
Si l'accord Paid Apps n'est pas actif, arrête-toi ici.

Tout le reste échouera silencieusement. C'est le blocage n°1 des premières mises en vente.

1

App Store Connect · créer les 4 produits

C'est ici qu'Apple « connaît » ce que tu vends. Les 4 IDs doivent être identiques au code, au caractère près.

Product IDTypePrixNom affiché
trainwise_pro_monthlyAbo · 1 mois9,99 €Trainwise Pro Mensuel
trainwise_pro_annualAbo · 1 an59,99 €Trainwise Pro Annuel
trainwise_coins_10Consommable2,99 €Pack 10 TrainCoins
trainwise_coins_50Consommable9,99 €Pack 50 TrainCoins
  • Créer le Subscription Group « Trainwise Pro » + les 2 abos
    Monetization → Subscriptions. Les 2 abos vont dans le même groupe (l'utilisateur ne peut en avoir qu'un actif).
  • Créer les 2 consommables coins
    Monetization → In-App Purchases → type « Consumable ».
  • Ajouter une App Review Screenshot à chacun des 4 produits
    C'est CE qui manquait au rejet 2.1(b). N'importe quel écran de l'app montrant l'achat (l'écran boutique). Sans capture, impossible de soumettre le produit.
  • Générer une In-App Purchase Key (pour RevenueCat)
    Users and Access → Integrations → In-App Purchase → « Generate ». Télécharge le fichier .p8 : RevenueCat en a besoin pour valider les achats. (À défaut, l'« App-Specific Shared Secret » fait l'affaire.)
2

RevenueCat · le projet + l'app

RevenueCat lit tes produits Apple grâce à la clé de l'étape précédente.

  • Créer le projet, puis + App → App Store
    Renseigne le bundle ID com.trainwise.appli.
  • Coller l'In-App Purchase Key (.p8) dans les réglages de l'app
    Sans elle, RevenueCat ne peut pas confirmer les achats → le webhook ne partira jamais.
3

RevenueCat · Products, Entitlement, Offering

L'étape qui embrouille tout le monde. Trois notions, dans cet ordre.

  • Products — importer les 4 depuis App Store Connect
    RevenueCat propose l'import automatique. Vérifie que les 4 IDs apparaissent à l'identique.
  • Entitlement — en créer UN, identifiant pro
    Attache-lui les 2 abos (trainwise_pro_monthly, trainwise_pro_annual). Les coins sont des consommables → on ne les attache PAS à un entitlement.
  • Offering — en créer un, identifiant default, marqué « Current »
    Ton code lit offerings.current : l'offering doit donc être celui par défaut.
  • Ajouter 4 Packages à l'offering (un par produit)
    Un package = un produit présenté dans la vitrine. Attention à leur identifiant → callout ci-dessous.
⚠️
LE piège qui fait croire que « RevenueCat marche pas »

Ton code fait packages.find(p => p.identifier === 'trainwise_pro_annual'). Donc l'identifiant de chaque package doit être exactement le Product ID — trainwise_pro_annual, trainwise_coins_10, etc. Surtout PAS les identifiants par défaut de RevenueCat ($rc_monthly, $rc_annual). Si tu laisses les défauts, l'app ne trouvera aucun produit et la boutique restera vide.

4

Les clés publiques → ton code

C'est le fameux appl_XXXX encore en placeholder qui bloque tout aujourd'hui.

  • RevenueCat → API Keys → copier la clé publique Apple appl_…
    C'est la clé publique (SDK), pas la secret key. Idem pour Android : goog_….
  • Remplacer les placeholders dans environment.prod.ts
    revenueCatAppleApiKey et revenueCatGoogleApiKey. Pense aussi à environment.ts et environment.staging.ts si tu testes dessus.
5

Le webhook → ton back Render

C'est lui qui crédite réellement les coins et active le Pro en base.

  • RevenueCat → Integrations → Webhooks → URL du webhook
    https://trainwise-backend-rnd4.onrender.com/api/subscription/webhook
  • Header Authorization = Bearer <ton-secret>
    Choisis un secret long et aléatoire. Le code compare la valeur à Bearer <secret> — le mot « Bearer » doit être inclus côté RevenueCat.
  • Sur Render → variable d'env REVENUECAT_WEBHOOK_SECRET = le même secret
    Sans « Bearer », juste la valeur brute. Puis redéploie le back.
🔒
Sécurité durcie côté back

Le webhook refuse désormais toute requête si REVENUECAT_WEBHOOK_SECRET n'est pas défini (avant, il était ouvert à tous → quelqu'un pouvait s'auto-créditer des coins). Donc cette variable est obligatoire, sinon le webhook répond 503.

6

Tester en Sandbox avant de soumettre

On vérifie la chaîne complète avec un faux achat, sans dépenser un centime.

  • Créer un Sandbox Tester
    App Store Connect → Users and Access → Sandbox → Testers. Un email bidon suffit.
  • Acheter un pack coins + un abo avec le compte sandbox
    Sur l'app installée via TestFlight ou build de dev. Vérifie que le solde de TrainCoins augmente et que le badge PRO s'affiche.
  • Vérifier les logs Render : le webhook a bien été reçu
    Tu dois voir l'event INITIAL_PURCHASE / NON_SUBSCRIPTION_PURCHASE traité. RevenueCat a aussi un onglet « Events » pour voir les livraisons.
  • Tester le bouton Restaurer les achats
    Obligatoire pour Apple. Il doit re-débloquer le Pro sans re-payer.
7

Re-soumettre à Apple

On répond aux deux rejets d'un coup.

  • Rattacher les 4 IAP à la version de l'app (bouton « + »)
    Sur une première soumission, les IAP doivent partir en review AVEC le binaire. C'était la cause du rejet 2.1(b).
  • Uploader le nouveau build (clés remplies + suppression de compte durcie)
    Un nouveau binaire est de toute façon exigé pour relancer la review.
  • Compte démo actif + vidéo de suppression de compte dans les Notes
    Répond au rejet 5.1.1(v). Crée le vrai demo@trainwise-app.com et filme le flux Réglages → Zone de danger → Supprimer.
